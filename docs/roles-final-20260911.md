## 后端约定

- 服务机构继续使用内部 audience=manager，避免更名导致原路由和 ID 丢失。当前五类 category/resourceType 依次为 cro、cdmo、solution、ip_service、financing_service。仅修改面向用户的角色名称；首页数据中心“技术经理人”计数口径不随入口更名改变。
- 延用现有 category 与 resourceType 一一对应的结构。企业/科研的通用 service 资料不会自动改成新 CRO/CDMO 等类型；本轮没有足够资料证明它们属于哪种具体服务，也不新增演示发布数据。
- categories 是当前可显示的分类。legacyCategories 仅用于既有历史资料编辑；preservedFiltersByCategory 仅用于原属性验证和保留。小程序不要把后两项画成入口。
- 公开列表和带专区的“all”聚合只包含当前开放分类。显式请求 manager/achievement、scientist/finance 的公开列表返回 400；原已发布成果详情 ID 继续兼容。
- 不改公共 API 路径：/api/catalogs/{audience}、/api/resources、/api/resources/{id}。筛选参数依旧使用 filter.key，展示/保存值使用 filter.field，未声明 field 时使用 key。
- 科研发生调整的字段使用 scientist 前缀，投资人字段使用 investor 前缀，保护共享资源的旧属性与企业属性。patentType、patentStatus、talentMaturity 仍为相同事实定义，继续复用。
- investorIndications 为数组；管理端可填写多个，小程序筛选仍提交单个 indication 字符串，服务端按包含关系匹配。查询不接受逗号拼接的多值或任意数组参数。
- 交易意向是原 kind：产出=supply、诉求=demand，资源仍必须有供需类型。其他三级属性可空；发布后出现在专栏，具体筛选仅匹配已填写的有效值，多条件为 AND。
- 场景、骊珠整体解决方案、投融资服务保留图中的排序（默认排序/最新发布）；其他新分类不加图外排序栏。后台编辑表单不将排序保存成业务属性。

## 历史成果处理

旧技术经理人资源保留为 achievement，保留正文、属性、关联、发布状态和排序，不自动转换成新服务。它们从新服务分类及聚合列表退出，可在管理后台“查看全部资源”中维护。既有记录编辑时才提供“历史成果（原技术经理人）”，新建服务不能选它。

历史成果即使没有专区关联，也必须打开为原成果类型；保存不能默认变成项目或 CRO。原项目池的自定义行业/合作标签继续保留。以上两条均有实际表单回归，经历先失败、后修复验证。

科研投融资按图中的“后续补充”保留占位；没有编造筛选项或投融资记录。若用户后续补充分类，再单独开放。
